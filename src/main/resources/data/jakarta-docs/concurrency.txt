Jakarta Concurrency 3.1

Jakarta Concurrency provides a standard way to run asynchronous and concurrent tasks in Jakarta EE applications using managed executors.

Core Concepts:
- ManagedExecutorService: A container-managed executor that runs tasks with proper context propagation (security, transactions, class loading). Inject it with @Inject.
- ManagedThreadFactory: Creates container-managed threads with context propagation.
- @Asynchronous: Annotate methods to run them asynchronously. The container manages the execution.
- Context Service: Propagates Jakarta EE context to executed tasks.

Virtual Threads Integration (Java 21+):
Jakarta Concurrency 3.1 supports virtual threads. Virtual threads are lightweight threads managed by the JVM, not the OS. They cost approximately 1KB of heap vs 1MB for platform threads. This means you can create millions of virtual threads without exhausting memory.

Key benefits for Jakarta EE applications:
- Thread-per-request model becomes viable: Each HTTP request gets its own virtual thread. No thread pool tuning needed.
- Blocking I/O is cheap: Virtual threads yield when they block on I/O, freeing the carrier thread for other work.
- Simplified concurrency: No need for reactive patterns or CompletableFuture chains for simple blocking operations.

Configuration in Payara:
Configure managed executors to use virtual threads via the Payara admin console or deployment descriptors. Set the virtual-thread-enabled property to true on your ManagedExecutorService.

Caveats:
Avoid synchronized blocks that hold locks during I/O operations (pinning). Use java.util.concurrent.locks.ReentrantLock instead. Virtual threads are not for CPU-bound work; they help with I/O-bound tasks like HTTP calls, database queries, and file operations.

Best Practices:
Use virtual threads for I/O-bound operations (calling external APIs, database queries). Use platform threads for CPU-bound work (encryption, image processing). Monitor virtual thread creation with JFR (Java Flight Recorder) events.
