The Pitch

Why local AI inside Jakarta EE

Let me set the stage before we get into code. Why are we even talking about AI inside a monolith? The standard pattern for AI integration in Java applications is to call an external API. You send your data to OpenAI or Anthropic or whoever, they run the model, send back a response. It works. But it comes with tradeoffs that matter in enterprise settings.

The Problem with AI Integration

Typical AI Integration

  • External API calls (OpenAI, Anthropic)
  • Data leaves your network
  • API costs scale with usage
  • Vendor lock-in
  • Network latency on every request
  • Python dependency for AI services

What If AI Was Local?

  • Zero data leaves the JVM
  • No API costs. Ever.
  • No vendor dependencies
  • No network round-trips to external APIs
  • Pure Java. No Python.
  • Deploys like any Jakarta EE app

Let's be honest about the typical AI integration pattern. You've got your nice Jakarta EE application, clean architecture, everything runs inside your network. Then someone says "we need AI." Next thing you know, you're sending user queries to an external API. Your data leaves your network. You're paying per token, which means your costs scale linearly with usage and you can't predict them. You're coupled to a vendor's API format, pricing model, and uptime. And somewhere in your stack, someone spun up a Python microservice just to talk to the LLM because the examples are all in Python.

Now look at the right side. What if the model ran inside your infrastructure? Zero data leaves your network because the inference happens on your hardware. No API costs because there's no API. No vendor lock-in because you're running an open-source model. No network round-trips to external services. And it's pure Java. No Python runtime to manage, no pip dependency hell, no separate team to maintain the "AI service."

This isn't hypothetical. This is what we're going to build today.

No Python. No API Key. No Microservice.

Four moving parts, all connected. The browser talks to Payara Micro using HTMX. No JavaScript framework. HTMX sends form posts, Payara returns HTML fragments, HTMX swaps them into the DOM. That's the entire frontend.

Inside Payara, CDI manages the AI beans. LangChain4j provides the RAG pipeline. It talks to Ollama over HTTP for inference. And PgVector in PostgreSQL stores the vector embeddings.

This is important for the regulated industries in the room. No new database to audit. No new data flow to secure. The embeddings are just rows in a PostgreSQL table.

Step one. A single class. One annotation. This is standard Jakarta EE, nothing AI-specific yet. The @DataSourceDefinition annotation declares a PostgreSQL datasource that Payara will manage.

The interesting bit is what this datasource connects to. We're using the pgvector Docker image, which is standard PostgreSQL with the vector extension pre-installed. The extension gets enabled at startup with a single SQL command: CREATE EXTENSION IF NOT EXISTS vector. That one command adds vector similarity search to PostgreSQL. No separate vector database needed.

If you're already running PostgreSQL in production, you just install the extension and you have a vector database. Same connection pool, same JDBC driver, same everything.

Step 2: CDI Producers for AI Beans

@ApplicationScoped
public class EmbeddingProducers {

    @Resource(lookup = "java:app/ocx-db")
    DataSource dataSource;

    @Produces @ApplicationScoped
    public EmbeddingModel embeddingModel() {
        return OllamaEmbeddingModel.builder()
            .baseUrl(ollamaBaseUrl)
            .modelName("nomic-embed-text")
            .build();
    }

    @Produces @ApplicationScoped
    public EmbeddingStore<TextSegment> embeddingStore() {
        return PgVectorEmbeddingStore.datasourceBuilder()
            .datasource(dataSource)
            .dimension(768)
            .table("embeddings")
            .createTable(true)
            .build();
    }
}

Step two. This is where CDI starts pulling its weight. Three producer methods in one class. The first creates an OllamaEmbeddingModel, configured with the model name "nomic-embed-text" and a timeout. The OLLAMA_BASE_URL comes from MicroProfile Config, which means you can override it with an environment variable without rebuilding.

The second producer creates a PgVectorEmbeddingStore. Notice it uses the same DataSource from step one. The dimension is 768 because that's what nomic-embed-text outputs. createTable(true) means it creates the vector table automatically on first run. You don't need to run DDL scripts.

The third producer, which I'll show on the next slide, creates the ContentRetriever. But look at what we've achieved already: EmbeddingModel and EmbeddingStore are now CDI beans. Any class in the application can @Inject them. That's the CDI advantage. The AI infrastructure is wired the same way you wire a database or a message queue.

Load & Embed

@Transactional
void init(@Observes @Initialized(...) Object e) {
  // 1. Persist as JPA entities
  List<DocumentEntity> docs =
    persistDocuments();

  // 2. Split & embed into vectors
  DocumentSplitter splitter =
    DocumentSplitters.recursive(500, 100);

  embeddingStore.addAll(embeddings, segments);

Same database. JPA entities for structured queries. PgVector for semantic search. One DataSource, two access patterns.

Step four is where the monolith story gets concrete. On the left, a standard JPA entity. Nothing special. Title, source, content, timestamp. Standard Jakarta Persistence 3.2. This goes into a relational table called "documents."

On the right, the ingestion flow. When the application starts, a CDI event fires this method. First, we persist the documents as JPA entities using EntityManager. Standard JPA. Then we read those same entities, split their content into overlapping chunks, generate vector embeddings, and store them in PgVector.

This is the key architectural point. The same PostgreSQL database holds both the relational document table and the vector embeddings table. Same datasource. Same connection pool. Same backups. You can query documents by title with JPQL, or search them by semantic similarity with PgVector. Two access patterns, one database.

The duplicate guard checks if documents already exist before re-ingesting. App restarts are safe. If you want to re-ingest, the run.sh truncate command clears both tables.

The Wiring

@ApplicationScoped
public class ConferenceChatService {

  @Inject ChatModel chatModel;
  @Inject ContentRetriever contentRetriever;

  private ConferenceAssistant assistant;

  @PostConstruct
  void init() {
    assistant = AiServices.builder(
        ConferenceAssistant.class)
      .chatModel(chatModel)
      .contentRetriever(contentRetriever)
      .build();
  }
}

An interface with annotations becomes an AI service. LangChain4j generates the implementation at runtime.

Step five. This is the heart of the demo. On the left, an interface. That's it. An interface with two annotations. @SystemMessage defines the AI's behavior. @UserMessage marks the parameter as the user's question. LangChain4j generates the implementation at runtime. You never write an implementation class.

On the right, the wiring. In a @PostConstruct method, we use AiServices.builder() to create the implementation. We pass the chat model and the content retriever. That's the RAG connection. When someone calls assistant.ask("What is CDI?"), LangChain4j does three things: it calls the content retriever to find relevant context from our vector store, it constructs a prompt that combines the system message, the retrieved context, and the user's question, and it sends that prompt to the chat model. The response comes back as a string.

The greeting detection is a small detail worth mentioning. If someone types "hello," we don't want to run RAG. There's nothing to retrieve. So we detect greetings and use the raw ChatModel with a warm prompt instead. It's a minor UX touch that prevents the AI from searching for "hello" in the vector store.

That's the complete RAG pipeline. Interface plus builder. The rest of the application is CDI configuration and a JAX-RS endpoint.

Step 5: Expose the Chat Endpoint

@Path("/chat")
public class ChatResource {

    @Inject ConferenceChatService chatService;

    @POST
    @Consumes(APPLICATION_FORM_URLENCODED)
    @Produces(TEXT_HTML)
    public String ask(@FormParam("question") String question) {
        String answer = chatService.ask(question);
        return renderAnswer(question, answer);
    }

    private String renderAnswer(String question, String answer) {
        Node document = PARSER.parse(answer);
        String html = RENDERER.render(document);
        return """
            <div class="chat-message">
              <div class="question">%s</div>
              <div class="answer">%s</div>
            </div>""".formatted(escapeHtml(question), html);
    }
}

Step six. A standard JAX-RS resource. POST endpoint, consumes form-encoded data, produces HTML. The question comes in as a form parameter from HTMX. We call the chat service, get the answer, render it, and return HTML.

The rendering is worth noting. LLMs return markdown. We need HTML for the browser. CommonMark parses the markdown and renders it to HTML server-side. The question gets HTML-escaped because user input should never be trusted. The answer doesn't need escaping because it comes from our local LLM, not from user input.

On the frontend, HTMX takes this HTML fragment and swaps it into the DOM. The hx-swap="afterbegin" attribute means new messages appear at the top. No JSON API, no client-side template rendering, no virtual DOM diffing. The server sends HTML and the browser displays it. The way the web was designed to work.

Beyond RAG

From declarative to agentic to self-contained

Step 1 gave us a working RAG pipeline. But it's a single-shot process: embed query, retrieve chunks, generate answer. No decision-making. No iteration. The assistant can't decide HOW to answer. That changes now.

We're going to add three more modes, each progressively smarter. And here's the key: every mode runs inside the same WAR. Same CDI beans. Same JAX-RS endpoints. We're just swapping what happens when someone asks a question.

Same WAR. Same CDI beans. Same JAX-RS endpoints. One switch statement decides the mode.

return switch (mode) {
    case "agent"        -> agent.ask(question);          // Mode 2
    case "orchestrated" -> orchestrator.ask(question);   // Mode 3
    case "in-process"   -> askInProcess(question);       // Mode 4
    default             -> askDeclarative(question);     // Mode 1
};

Here's the progression. Mode 1 is what we just built: declarative RAG. A single AiServices interface backed by PgVector retrieval. It works, but it always retrieves, even for "hello."

Mode 2 adds a state graph. The LLM classifies each query and decides whether RAG is needed. Greetings go direct. Spec questions go through retrieval. This is agentic behavior: the assistant decides HOW to answer.

Mode 3 composes multiple specialist agents. A planner agent decomposes the question and delegates to a spec expert, a version checker, or a code generator. Each specialist has its own tools. This is agents-calling-agents.

Mode 4 is the endgame: remove Ollama entirely. Jlama runs LLM inference inside the JVM using the Panama Vector API. No external process. No Python. No network hop. The WAR is the inference server.

And the routing? It's literally one switch statement in ConferenceChatService. That's the CDI advantage. Every mode is a bean. The service picks which bean to call.

Step 2: Agentic Workflow

LangGraph4j - The assistant decides HOW to answer

START
→
Classify LLM categorizes query
→
routing decision
RAG Retrieve context
Direct Skip retrieval
→
Respond Generate answer
→
END

Cyclical execution. The LLM classifies the query, then routes to the appropriate path. Not a single prompt-response. A state machine.

Step 1 was a straight line: embed, retrieve, generate. Step 2 introduces branching. The graph has four nodes. The first node, classify, asks the LLM to categorize the query. Is this a specification question that needs RAG? Or is it a greeting that can be answered directly?

Based on the classification, the graph routes to either the RAG node or the direct node. The RAG node retrieves context from PgVector. The direct node skips retrieval entirely. Both paths converge on the respond node, which generates the final answer.

This is the fundamental shift from declarative to agentic. In Step 1, the pipeline always runs the same way. In Step 2, the LLM decides the execution path. It's a state machine where the transitions are determined by the LLM's classification.

LangGraph4j makes this easy. You define nodes as functions, edges as routing functions, and the framework handles the execution. The compiled graph is a CDI bean, initialized once in PostConstruct.

LangGraph4j: Building the State Graph

@ApplicationScoped
public class ConferenceAgent {

    @Inject ChatModel chatModel;
    @Inject ContentRetriever contentRetriever;
    private CompiledGraph<AgentState> workflow;

    @PostConstruct
    void init() {
        Map<String, Channel<?>> schema = Map.of(
            "query",          Channels.base(() -> ""),
            "classification", Channels.base(() -> ""),
            "context",        Channels.base(() -> ""),
            "response",       Channels.base(() -> "")
        );

        this.workflow = new StateGraph<>(schema, AgentState::new)
            .addNode("classify", AsyncNodeAction.node_async(classifyNode()))
            .addNode("rag",      AsyncNodeAction.node_async(ragNode()))
            .addNode("direct",   AsyncNodeAction.node_async(directNode()))
            .addNode("respond",  AsyncNodeAction.node_async(respondNode()))
            .addEdge(START, "classify")
            .addConditionalEdges("classify",
                AsyncEdgeAction.edge_async(routeByClassification()),
                Map.of("rag", "rag", "direct", "direct"))
            .addEdge("rag", "respond")
            .addEdge("direct", "respond")
            .addEdge("respond", END)
            .compile();
    }
}

Here's the graph definition. Four nodes. The classify node sends the query to the LLM and gets back "rag" or "direct". The conditional edge after classify routes based on that classification. The rag node retrieves context from PgVector. The direct node returns empty context. Both paths converge on respond, which generates the final answer.

The schema defines the state that flows through the graph. Four channels: the original query, the classification result, the retrieved context, and the final response. Each node reads and writes to this shared state.

Notice this is all CDI. ApplicationScoped bean. PostConstruct compiles the graph once. ChatModel and ContentRetriever are injected. The graph is compiled at startup and reused for every request. No per-request setup cost.

Koog - Specialists orchestrated by a planner

User Query
→

↓

The planner decomposes the question, picks the right specialist(s), and synthesizes the results.

Step 2 had one agent with branching logic. Step 3 composes multiple specialist agents into one orchestrator. Koog, from JetBrains, provides the planner agent pattern.

The planner receives the user's question, analyzes it, and decides which specialist tools to invoke. It can call them in sequence or in parallel. Then it synthesizes the results into a coherent answer.

Three specialist tools. SpecSearchTool wraps our existing ContentRetriever, so it reuses the PgVector RAG pipeline from Step 1. VersionCheckTool has static data about 18 Jakarta EE specifications and their version history. CodeExampleTool delegates to the LLM with a code-generation system prompt.

The planner agent is itself an LLM. It has a system prompt that explains when to use each tool. It decides based on the question. "Explain CDI events" triggers SpecSearchTool. "When was @DataSourceDefinition added?" triggers VersionCheckTool. "Show me a CDI producer example" triggers both SpecSearchTool and CodeExampleTool.

Koog Tools: Annotate and Delegate

Tool Definition

public class SpecSearchTool
    implements ToolSet {

  private final ContentRetriever retriever;

  @Tool
  @LLMDescription("Search Jakarta EE "
    + "spec documents for info")
  public String searchSpecs(
    @LLMDescription("The search query")
    String query) {

    var contents = retriever
      .retrieve(Query.from(query));
    return contents.stream()
      .map(c -> c.textSegment().text())
      .collect(Collectors.joining("\n\n"));
  }
}

Orchestrator Wiring

@ApplicationScoped
public class ConferenceOrchestrator {

  @Inject ChatModel chatModel;
  @Inject ContentRetriever contentRetriever;

  private AIAgent<String, String> planner;

  @PostConstruct
  void init() {
    ToolRegistry registry =
      new ToolRegistryBuilder()
        .tools(new SpecSearchTool(contentRetriever))
        .tools(new VersionCheckTool())
        .tools(new CodeExampleTool(chatModel))
        .build();

    this.planner = AIAgent.builder()
      .promptExecutor(executor)
      .llmModel(model)
      .systemPrompt("You are an orchestrator...")
      .toolRegistry(registry)
      .build();
  }
}

ToolSet + @Tool = declarative tool definition. ToolRegistryBuilder discovers tools via reflection. Pure Java, no Kotlin needed.

On the left, a tool definition. A class that implements ToolSet with methods annotated @Tool and @LLMDescription. The LLM reads the description to decide when to call the tool. The method body is plain Java. This one wraps our existing ContentRetriever.

On the right, the orchestrator wiring. Three tools registered in a ToolRegistry. The registry discovers the @Tool annotations via reflection. Then the AIAgent builder receives the registry, a system prompt, and an Ollama executor. The planner agent is a CDI bean, initialized once.

Key detail: this is pure Java. Koog is Kotlin-first, but AIAgent.run() is a non-suspend bridge method designed for Java interop. We proved this by decompiling the JAR and finding the Java-friendly entry point. No Kotlin compiler, no Kotlin runtime, no extra build steps.

Jlama: In-Process ChatModel

@ApplicationScoped
public class JlamaChatModelProducer {

    @Inject @ConfigProperty(name = "jlama.model.name",
                            defaultValue = "tjake/gemma-2b-it-jlama-Q4")
    String modelName;

    @Inject @ConfigProperty(name = "jlama.model.cache-path",
                            defaultValue = "/opt/jlama/models")
    String modelCachePath;

    private ChatModel jlamaChatModel;
    private boolean available;

    @PostConstruct
    void init() {
        try {
            this.jlamaChatModel = JlamaChatModel.builder()
                .modelName(modelName)
                .modelCachePath(Path.of(modelCachePath))
                .temperature(0.7f)
                .quantizeModelAtRuntime(true)
                .build();
            this.available = true;
        } catch (Exception e) {
            this.available = false; // graceful degradation
        }
    }
}

Same ChatModel interface as Ollama. Jlama implements it. The rest of the application works unchanged. Graceful degradation: if the model isn't available, modes 1-3 still work with Ollama.

Jlama uses the Panama Vector API (SIMD) for matrix multiplication. Requires Java 25 with --add-modules=jdk.incubator.vector. Pure Java, no native code, no JNI.

This is the entire Jlama integration. One CDI bean. A builder that creates a ChatModel backed by Jlama instead of Ollama. The model name references a quantized Gemma 2B on HuggingFace. Jlama downloads it on first use and caches it locally.

The key insight: JlamaChatModel implements the same ChatModel interface that Ollama uses. So every piece of code that injects ChatModel, which is all of modes 1-3, works with Jlama as the backing implementation. You don't change any other code. You just swap the producer.

The graceful degradation is important for the demo. If Jlama can't load, maybe the model isn't downloaded or the JVM doesn't have the Panama Vector API module, it sets available to false and logs a warning. The rest of the application works fine with Ollama. This means you can deploy the same WAR to environments with or without Jlama support.

04

Performance

CPU vs GPU. Ollama vs Jlama. Same WAR, different trade-offs.

Two performance dimensions. First, CPU vs GPU: the same WAR runs on both. Ollama handles GPU acceleration transparently. Change OLLAMA_BASE_URL, restart, done. This is the operational simplicity I keep coming back to. Your ops team doesn't need to learn a new deployment pattern. It's a Docker Compose file with different environment variables. The AI acceleration is an infrastructure concern, not an application concern.

Ollama vs Jlama

External process vs in-process inference

Ollama (Modes 1-3)

  • External HTTP process
  • Gemma 4 (2B parameters)
  • Network hop per inference
  • Separate container to manage
  • Higher quality answers

Jlama (Mode 4)

  • In-process, zero network
  • Gemma 2B quantized (Q4)
  • Panama Vector API (SIMD)
  • No external dependency
  • Fully self-contained

Same ChatModel interface. Same CDI injection point. The application doesn't know or care which backing implementation runs. Trade model size for operational simplicity.

This is the honest trade-off. Ollama runs a larger model (Gemma 4 with 2B parameters) as an external process. You get better answers, but you have a network hop and a separate container to manage. Jlama runs a smaller quantized model (Gemma 2B Q4) inside the JVM. You lose some answer quality, but you gain operational simplicity. Zero external dependencies.

The key point: the application code doesn't change. Both implement the same ChatModel interface. CDI injects whichever one is available. You can develop with Ollama for better answers and deploy with Jlama for self-contained operation. Or run both and let the user pick the mode.

For air-gapped environments, regulated industries, or edge deployments where you can't run a separate inference server, Jlama is the answer. For developer workstations where Ollama is easy to install, use Ollama. Same WAR either way.

Three containers. PostgreSQL with pgvector for both relational data and vector embeddings. Same database, two types of data. Ollama for model inference. And the application container, built with a multi-stage Dockerfile.

The PostgreSQL image is pgvector/pgvector:pg17. It's standard PostgreSQL 17 with the vector extension pre-installed. The healthcheck ensures the app doesn't start until PostgreSQL is ready.

Ollama pulls models on first run. gemma4:e2b is about 1.6 GB. nomic-embed-text is about 274 MB. Both get cached in a Docker volume, so subsequent starts are instant.

The app container has a dependency on both postgres and ollama. It won't start until postgres is healthy and ollama is running.

Multi-stage Dockerfile

FROM eclipse-temurin:25 AS build
WORKDIR /app
COPY pom.xml .
RUN ./mvnw dependency:go-offline -B
COPY src ./src
RUN ./mvnw clean package -DskipTests

FROM eclipse-temurin:25-jre
ARG PAYARA_VERSION=7.2026.3
ADD https://.../payara-micro-${PAYARA_VERSION}.jar /opt/payara/
COPY --from=build /app/target/ocx.war /opt/payara/deployments/ROOT.war
EXPOSE 8080
ENTRYPOINT ["java",
    "--add-modules=jdk.incubator.vector",
    "-jar", "/opt/payara/payara-micro.jar",
    "--deploy", "/opt/payara/deployments/ROOT.war",
    "--nocluster"]

Layer caching: pom.xml changes invalidate the dependency layer. Source changes only rebuild the application layer.

Two build stages. First stage uses Eclipse Temurin 21 to build the WAR. The trick is splitting the pom.xml copy from the src copy. Docker caches the dependency resolution layer separately. When you change source code, Docker only re-runs the package step, not the dependency download. This saves minutes on every rebuild.

Second stage uses the JRE-only image, which is smaller. Payara Micro is downloaded at build time, not runtime. The WAR is copied from the build stage. The entrypoint is a single java -jar command.

The net effect: your build server needs Docker, nothing else. No JDK, no Maven, no Payara installed on the host. Everything happens inside the container. This is the same pattern used by Cloud Native Buildpacks and Jib, but explicit and controlled.

One Command: ./run.sh deploy

$ ./run.sh deploy     # Full: postgres + ollama + app

  ✓ PostgreSQL is ready
  ✓ Enabling pgvector extension...
  ✓ Pulling AI models (first run only)...
  ✓ Infrastructure ready
  ✓ Application is ready

  http://localhost:8080

$ ./run.sh jlama      # Self-contained: postgres + app only

  ✓ PostgreSQL is ready
  ✓ Application is ready
  ✓ http://localhost:8080 (in-process AI, no Ollama)

Other commands: start, stop, logs, truncate, benchmark, clean

A single shell script wraps all the Docker Compose commands. ./run.sh deploy does everything: starts PostgreSQL and Ollama, enables the pgvector extension, pulls the AI models, builds and deploys the application, and waits for it to be ready.

For the self-contained mode, ./run.sh jlama skips Ollama entirely. Just PostgreSQL and the app. The Jlama model is downloaded on first inference inside the container. This is the intelligent monolith endgame: two containers, zero external AI services.

The other commands handle the lifecycle. truncate clears the embeddings table and re-ingests documents, useful when you update the source documents. benchmark runs the performance test and saves results. clean removes everything including volumes, giving you a fresh start.
