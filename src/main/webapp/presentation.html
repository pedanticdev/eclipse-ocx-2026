The Pitch

Why local AI inside Jakarta EE

Let me set the stage before we get into code. Why are we even talking about AI inside a monolith? The standard pattern for AI integration in Java applications is to call an external API. You send your data to OpenAI or Anthropic or whoever, they run the model, send back a response. It works. But it comes with tradeoffs that matter in enterprise settings.

The Problem with AI Integration

Typical AI Integration

  • External API calls (OpenAI, Anthropic)
  • Data leaves your network
  • API costs scale with usage
  • Vendor lock-in
  • Network latency on every request
  • Python dependency for AI services

What If AI Was Local?

  • Zero data leaves the JVM
  • No API costs. Ever.
  • No vendor dependencies
  • Sub-millisecond inference on GPU
  • Pure Java. No Python.
  • Deploys like any Jakarta EE app

Let's be honest about the typical AI integration pattern. You've got your nice Jakarta EE application, clean architecture, everything runs inside your network. Then someone says "we need AI." Next thing you know, you're sending user queries to an external API. Your data leaves your network. You're paying per token, which means your costs scale linearly with usage and you can't predict them. You're coupled to a vendor's API format, pricing model, and uptime. And somewhere in your stack, someone spun up a Python microservice just to talk to the LLM because the examples are all in Python.

Now look at the right side. What if the model ran inside your infrastructure? Zero data leaves your network because the inference happens on your hardware. No API costs because there's no API. No vendor lock-in because you're running an open-source model. Latency drops to single-digit milliseconds on GPU because there's no network hop. And it's pure Java. No Python runtime to manage, no pip dependency hell, no separate team to maintain the "AI service."

This isn't hypothetical. This is what we're going to build today.

No Python. No API Key. No Microservice.

Three things you won't need for this demo. No Python runtime. I have nothing against Python, but if your team writes Java, your AI infrastructure should speak Java too. No API key. The Stack

CDI, LangChain4j, Ollama, PgVector

Let me walk through the four pieces that make this work. The stack is deliberately small. Four technologies, each doing one thing well. If you're already running Jakarta EE and PostgreSQL in production, you're halfway there. You just need to add Ollama and the pgvector extension.

Four moving parts, all connected. The browser talks to Payara Micro using HTMX. No JavaScript framework. HTMX sends form posts, Payara returns HTML fragments, HTMX swaps them into the DOM. That's the entire frontend.

Inside Payara, CDI manages the AI beans. LangChain4j provides the RAG pipeline. It talks to Ollama over HTTP for inference. And PgVector in PostgreSQL stores the vector embeddings.

Notice there's no separate vector database. You don't need Pinecone or Weaviate or Milvus. pgvector is a PostgreSQL extension. It adds vector similarity search to the database you already run. Same instance, same backups, same connection pool, same operational model. Your embeddings live alongside your relational data.

This is important for the regulated industries in the room. No new database to audit. No new data flow to secure. The embeddings are just rows in a PostgreSQL table.

Every piece uses standard Jakarta EE APIs. Nothing custom or proprietary. CDI 4.1 producers create the embedding model, the vector store, and the content retriever as application-scoped beans. JAX-RS handles the chat endpoint and the benchmark endpoint. JPA 3.2 connects to PostgreSQL with the pgvector extension. The frontend is pure HTML with HTMX attributes. The server renders markdown to HTML using CommonMark before sending it to the browser. No React, no build step, no npm. The entire frontend is one HTML file, one CSS file, and the HTMX library.

This matters because it means any Java developer on your team can understand and maintain the whole stack. No context-switching between Java and JavaScript. No frontend build pipeline. Server-side rendering with progressive interactivity.

LangChain4j + Ollama

LangChain4j

  • Java-native LLM integration
  • RAG pipeline out of the box
  • CDI portable extension
  • Declarative AI services
  • Same patterns as LangChain (Python) but idiomatic Java

Ollama

  • Run LLMs locally
  • gemma4 for chat
  • nomic-embed-text for embeddings
  • CPU or GPU acceleration
  • Docker-friendly

ChatModel and EmbeddingModel are CDI beans, injected like any other dependency. Swap Ollama for another provider by changing one config property.

LangChain4j is the glue. It's the Java equivalent of LangChain in Python. Same patterns: document splitting, embedding, retrieval, response generation. But idiomatic Java. It has a CDI portable extension that auto-discovers model providers, so you don't wire things manually. In our case we use CDI producers to work around a generic type resolution issue in the extension, but the pattern is still clean.

Ollama is what makes local inference easy. It's a lightweight model server. You install it, pull a model with a single command, and it serves inference over a local HTTP endpoint. No CUDA setup, no model weight downloads from HuggingFace, no Python environment. Just "ollama pull gemma4" and you're running.

For this demo we use two models: gemma4:e2b for chat and nomic-embed-text for embeddings. Both are open-source. Both run on CPU or GPU. The embedding model produces 768-dimensional vectors, which is why our PgVector store is configured for dimension 768.

Why Ollama?

What Ollama Does

  • Runs LLMs locally with a single command
  • Handles model download, quantization, GPU detection
  • Exposes a simple HTTP API
  • Docker-friendly official image
  • Works on macOS, Linux, Windows (WSL2)

Alternatives

  • llama.cpp — lower-level, more control, more setup
  • vLLM — high-throughput serving, production-grade
  • LocalAI — OpenAI-compatible API, drop-in replacement
  • llamafile — single executable, zero install
  • GPT4All — desktop app, CPU-optimized

We chose Ollama for the demo because it's the simplest developer experience. Swap it for any of these alternatives by changing one CDI producer method. LangChain4j supports all of them.

Ollama isn't the only option. It's the easiest one. One command to install, one command to pull a model, and you have a local LLM running. It auto-detects your GPU, handles quantization, and serves a clean HTTP API.

But maybe you need something different. llama.cpp gives you more control over quantization and memory management. vLLM is designed for high-throughput production serving with batching and speculative decoding. LocalAI gives you an OpenAI-compatible API, so your existing code that calls OpenAI can point at LocalAI instead. llamafile is a single executable that bundles the model weights and runtime. GPT4All is optimized for CPU-only inference on laptops.

The key insight: all of these expose an HTTP endpoint. LangChain4j has integrations for all of them. Switching from Ollama to vLLM means changing one builder call in your CDI producer. The rest of the pipeline, the RAG pipeline, doesn't change at all.

In a production setting, I'd probably use vLLM behind a load balancer for the chat model, and keep Ollama for the embedding model since embedding is less latency-sensitive. But for this demo, Ollama handles both.

Live Build

From bare WAR to RAG in 6 steps

Now the fun part. I'm going to walk through exactly how this is built. Six incremental steps. Each step adds one capability on top of the previous one. By step 6, you have the complete RAG system.

The code you'll see is the actual code from the demo application. No simplifications, no "imagine this part is implemented." This is what runs when you hit localhost:8080.

I'll show each file and explain why it's structured that way. Pay attention to the CDI patterns, because that's where the magic happens.

Step 1: Define the DataSource

@ApplicationScoped
@DataSourceDefinition(
    name = "java:app/ocx-db",
    className = "org.postgresql.ds.PGSimpleDataSource",
    serverName = "postgres",
    portNumber = 5432,
    databaseName = "ocx",

Standard Jakarta EE @DataSourceDefinition. PostgreSQL with pgvector extension.

Step one. A single class. One annotation. This is standard Jakarta EE, nothing AI-specific yet. The @DataSourceDefinition annotation declares a PostgreSQL datasource that Payara will manage.

The interesting bit is what this datasource connects to. We're using the pgvector Docker image, which is standard PostgreSQL with the vector extension pre-installed. The extension gets enabled at startup with a single SQL command: CREATE EXTENSION IF NOT EXISTS vector. That one command adds vector similarity search to PostgreSQL. No separate vector database needed.

If you're already running PostgreSQL in production, you just install the extension and you have a vector database. Same connection pool, same JDBC driver, same everything.

Step 2: CDI Producers for AI Beans

@ApplicationScoped
public class EmbeddingProducers {

    @Resource(lookup = "java:app/ocx-db")
    DataSource dataSource;

    @Produces @ApplicationScoped
    public EmbeddingModel embeddingModel() {
        return OllamaEmbeddingModel.builder()
            .baseUrl(ollamaBaseUrl)
            .modelName("nomic-embed-text")
            .build();
    }

    @Produces @ApplicationScoped
    public EmbeddingStore<TextSegment> embeddingStore() {
        return PgVectorEmbeddingStore.datasourceBuilder()
            .datasource(dataSource)
            .dimension(768)
            .table("embeddings")
            .createTable(true)
            .build();
    }
}

Step two. This is where CDI starts pulling its weight. Three producer methods in one class. The first creates an OllamaEmbeddingModel, configured with the model name "nomic-embed-text" and a timeout. The OLLAMA_BASE_URL comes from MicroProfile Config, which means you can override it with an environment variable without rebuilding.

The second producer creates a PgVectorEmbeddingStore. Notice it uses the same DataSource from step one. The dimension is 768 because that's what nomic-embed-text outputs. createTable(true) means it creates the vector table automatically on first run. You don't need to run DDL scripts.

The third producer, which I'll show on the next slide, creates the ContentRetriever. But look at what we've achieved already: EmbeddingModel and EmbeddingStore are now CDI beans. Any class in the application can @Inject them. That's the CDI advantage. The AI infrastructure is wired the same way you wire a database or a message queue.

Step 3: Wire the Content Retriever

@Produces @ApplicationScoped
public ContentRetriever contentRetriever(
        EmbeddingStore<TextSegment> store,
        EmbeddingModel model) {
    return EmbeddingStoreContentRetriever.builder()
        .embeddingStore(store)
        .embeddingModel(model)
        .maxResults(5)
        .minScore(0.5)
        .build();
}

The retriever finds the top 5 most similar segments with a minimum relevance score of 0.5. CDI injects both the store and model from our producers.

Step three. The ContentRetriever is the retrieval part of RAG. It takes a user's question, embeds it using the EmbeddingModel, searches the EmbeddingStore for the most similar segments, and returns the top results.

Two tuning knobs: maxResults controls how many segments to retrieve. We use 5. minScore sets the relevance threshold. We use 0.5 on a 0-to-1 scale. Anything below 0.5 similarity gets filtered out. This prevents irrelevant results from polluting the LLM's context window.

The CDI magic here: both the store and the model are method parameters. CDI resolves them from the producers we defined in step two. You don't pass them explicitly. You just declare what you need and CDI provides it.

Step 4: Ingest Documents on Startup

@ApplicationScoped
public class DataLoader {

    @Inject EmbeddingModel embeddingModel;
    @Inject EmbeddingStore<TextSegment> embeddingStore;

    void init(@Observes @Initialized(ApplicationScoped.class) Object event) {
        List<Document> documents = loadJakartaDocs();
        DocumentSplitter splitter = DocumentSplitters.recursive(500, 100);
        List<TextSegment> segments = split(documents, splitter);

        List<Embedding> embeddings = embeddingModel.embedAll(segments).content();
        embeddingStore.addAll(embeddings, segments);
    }
}

CDI event observer triggers ingestion when the application scope initializes. Documents are split into 500-character overlapping segments, embedded, and stored.

Step four. Data ingestion. When the CDI application scope initializes, this observer method fires. It loads Jakarta EE specification documents from the classpath, splits them into overlapping chunks of about 500 characters, generates embeddings for all chunks, and stores them in PgVector.

The DocumentSplitter uses recursive splitting, which means it tries to split on paragraph boundaries first, then sentence boundaries, then word boundaries. The 100-character overlap ensures that context isn't lost at chunk boundaries. A sentence that spans two chunks will appear in both, which improves retrieval quality.

In production, you wouldn't load from the classpath. You'd load from a database, or a file system, or an S3 bucket. LangChain4j has document loaders for all of those. The ingestion pattern stays the same: load, split, embed, store.

For this demo, we load five Jakarta EE specification excerpts. CDI, JPA, Concurrency, Jakarta Data, and JAX-RS. That gives the RAG system enough domain knowledge to answer questions about Jakarta EE APIs.

Step 5: Define the AI Service

The Interface

@SystemMessage("""
  You are a Jakarta EE expert
  assistant. Answer questions
  using the provided context.
  Be concise.
  """)
public interface ConferenceAssistant {
    String ask(@UserMessage String question);
}

The Wiring

@ApplicationScoped
public class ConferenceChatService {

  @Inject ChatModel chatModel;
  @Inject ContentRetriever contentRetriever;

  private ConferenceAssistant assistant;

  @PostConstruct
  void init() {
    assistant = AiServices.builder(
        ConferenceAssistant.class)
      .chatModel(chatModel)
      .contentRetriever(contentRetriever)
      .build();
  }
}

An interface with annotations becomes an AI service. LangChain4j generates the implementation at runtime.

Step five. This is the heart of the demo. On the left, an interface. That's it. An interface with two annotations. @SystemMessage defines the AI's behavior. @UserMessage marks the parameter as the user's question. LangChain4j generates the implementation at runtime. You never write an implementation class.

On the right, the wiring. In a @PostConstruct method, we use AiServices.builder() to create the implementation. We pass the chat model and the content retriever. That's the RAG connection. When someone calls assistant.ask("What is CDI?"), LangChain4j does three things: it calls the content retriever to find relevant context from our vector store, it constructs a prompt that combines the system message, the retrieved context, and the user's question, and it sends that prompt to the chat model. The response comes back as a string.

The greeting detection is a small detail worth mentioning. If someone types "hello," we don't want to run RAG. There's nothing to retrieve. So we detect greetings and use the raw ChatModel with a warm prompt instead. It's a minor UX touch that prevents the AI from searching for "hello" in the vector store.

That's the complete RAG pipeline. Interface plus builder. The rest of the application is CDI configuration and a JAX-RS endpoint.

Step 6: Expose the Chat Endpoint

@Path("/chat")
public class ChatResource {

    @Inject ConferenceChatService chatService;

    @POST
    @Consumes(APPLICATION_FORM_URLENCODED)
    @Produces(TEXT_HTML)
    public String ask(@FormParam("question") String question) {
        String answer = chatService.ask(question);
        return renderAnswer(question, answer);
    }

    private String renderAnswer(String question, String answer) {
        Node document = PARSER.parse(answer);
        String html = RENDERER.render(document);
        return """
            <div class="chat-message">
              <div class="question">%s</div>
              <div class="answer">%s</div>
            </div>""".formatted(escapeHtml(question), html);
    }
}

Step six. A standard JAX-RS resource. POST endpoint, consumes form-encoded data, produces HTML. The question comes in as a form parameter from HTMX. We call the chat service, get the answer, render it, and return HTML.

The rendering is worth noting. LLMs return markdown. We need HTML for the browser. CommonMark parses the markdown and renders it to HTML server-side. The question gets HTML-escaped because user input should never be trusted. The answer doesn't need escaping because it comes from our local LLM, not from user input.

On the frontend, HTMX takes this HTML fragment and swaps it into the DOM. The hx-swap="afterbegin" attribute means new messages appear at the top. No JSON API, no client-side template rendering, no virtual DOM diffing. The server sends HTML and the browser displays it. The way the web was designed to work.

And that's it. Six steps. From a datasource definition to a working RAG chat interface. Let me show you the summary.

CPU vs GPU

Same WAR. Zero code changes. Only OLLAMA_BASE_URL changed.

Here's where the deployment story gets interesting. The same WAR file runs on both CPU-only hardware and GPU-accelerated hardware. The only thing that changes is where Ollama runs. On your dev laptop, Ollama runs on CPU. On a production server with a GPU, Ollama runs on GPU. Same WAR. Same code. Zero changes.

This is the Jakarta EE promise applied to AI. Write once, run anywhere. Your application doesn't know or care what hardware the model runs on. It just calls OLLAMA_BASE_URL. The Ollama instance behind that URL handles GPU detection and acceleration transparently.

The benchmark measures two operations that represent the AI workload. First, embedding five text segments. This tests the embedding model's throughput. Second, generating a fifty-word chat response. This tests the LLM's inference speed.

We measure latency in milliseconds and calculate tokens per second. The benchmark runs on CPU hardware first, saving results to a JSON file. Then the same WAR deploys against a GPU-accelerated Ollama instance, runs the same benchmark, and saves those results.

Both result sets go into a static JSON file that gets bundled into the WAR. The comparison table loads it at runtime. The methodology is simple: same code, same models, same prompts. The only variable is the hardware.

This is relevant because it demonstrates that you can develop on a laptop with CPU-only Ollama and deploy to a GPU server without changing anything in your application. The performance scales with the hardware, not the code.

This is the operational simplicity I keep coming back to. Your ops team doesn't need to learn a new deployment pattern. It's a Docker Compose file with different environment variables. The AI acceleration is an infrastructure concern, not an application concern.

Three containers. PostgreSQL with pgvector for both relational data and vector embeddings. Same database, two types of data. Ollama for model inference. And the application container, built with a multi-stage Dockerfile.

The PostgreSQL image is pgvector/pgvector:pg17. It's standard PostgreSQL 17 with the vector extension pre-installed. The healthcheck ensures the app doesn't start until PostgreSQL is ready.

Ollama pulls models on first run. gemma4:e2b is about 1.6 GB. nomic-embed-text is about 274 MB. Both get cached in a Docker volume, so subsequent starts are instant.

The app container has a dependency on both postgres and ollama. It won't start until postgres is healthy and ollama is running.

Multi-stage Dockerfile

FROM eclipse-temurin:21 AS build
WORKDIR /app
COPY pom.xml .
RUN ./mvnw dependency:go-offline -B
COPY src ./src
RUN ./mvnw clean package -DskipTests

FROM eclipse-temurin:21-jre
ARG PAYARA_VERSION=7.2026.3
ADD https://.../payara-micro-${PAYARA_VERSION}.jar /opt/payara/
COPY --from=build /app/target/ocx.war /opt/payara/deployments/ROOT.war
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/opt/payara/payara-micro.jar",
            "--deploy", "/opt/payara/deployments/ROOT.war",
            "--nocluster"]

Layer caching: pom.xml changes invalidate the dependency layer. Source changes only rebuild the application layer.

Two build stages. First stage uses Eclipse Temurin 21 to build the WAR. The trick is splitting the pom.xml copy from the src copy. Docker caches the dependency resolution layer separately. When you change source code, Docker only re-runs the package step, not the dependency download. This saves minutes on every rebuild.

Second stage uses the JRE-only image, which is smaller. Payara Micro is downloaded at build time, not runtime. The WAR is copied from the build stage. The entrypoint is a single java -jar command.

The net effect: your build server needs Docker, nothing else. No JDK, no Maven, no Payara installed on the host. Everything happens inside the container. This is the same pattern used by Cloud Native Buildpacks and Jib, but explicit and controlled.

Other commands: start, stop, logs, truncate, benchmark, clean

A single shell script wraps all the Docker Compose commands. ./run.sh deploy does everything: starts PostgreSQL and Ollama, enables the pgvector extension, pulls the AI models, builds and deploys the application, and waits for it to be ready.

The other commands handle the lifecycle. truncate clears the embeddings table and re-ingests documents, useful when you update the source documents. benchmark runs the performance test against the current Ollama instance and saves results. clean removes everything including volumes, giving you a fresh start.

This is deliberate. For a conference demo, the audience should be able to go from zero to running in one command. No prerequisite setup. No manual configuration. Clone, run, done.

And in a real deployment, you'd replace this with whatever your CI/CD pipeline does. Helm chart, Kubernetes manifest, Terraform module. The application is a standard WAR. It deploys the same way everything else deploys.
