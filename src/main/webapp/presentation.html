The Claim

Boring stack. Smart AI.

Let me set the stage. The standard narrative: you want AI, you need Python, a vector database, a separate service, and a thread pool tuned to your CPU cores. I'm going to challenge every one of those assumptions with working code.

Three problems I keep hearing. Thread pools: your Java app makes blocking HTTP calls to the LLM. Each call ties up a platform thread for seconds. Pool too small? Requests queue. Pool too big? You run out of memory. Vector data: embeddings are arrays of 768 floats. JPA doesn't have a vector column type, so people say you need a vector database. Python: every AI tutorial is Python. Your team writes Java. Now you need two ecosystems.

None of these are unsolvable. They're architectural decisions, and the standard answers are overengineered.

The Boring Stack is the Smartest Choice

No Vector DB
No Python
No Thread Pool Tuning

Virtual threads handle concurrency. Jakarta Data handles persistence. Java handles similarity. Same spec, new capabilities.

Three things you won't need. No separate vector database. Embeddings are stored as byte arrays in a JPA entity, queried through Jakarta Data repositories. Similarity search is 15 lines of Java. No Python. LangChain4j is the Java-native equivalent of Python's LangChain. No thread pool tuning. Virtual threads on Java 21 give you millions of concurrent tasks without configuring a single pool size.

This is the counter-claim. Your existing Jakarta EE knowledge, the stuff your team already knows, composes naturally with AI workloads. You don't need to learn a new stack. You need to use the one you have correctly.

Two layers. Top row is the request flow: browser to Payara to AiService to Ollama. Bottom row is the data layer: PostgreSQL with Jakarta Data repositories for persistence, VectorSearch for similarity, virtual threads for parallelism.

No PgVector extension. No separate vector database. Embeddings are stored as byte arrays in a standard JPA entity. The VectorSearch class loads all chunks from the repository, computes cosine similarity against the query embedding in Java, and returns the top matches. For a few hundred chunks, this is instantaneous. For production scale with millions of vectors, you'd want a vector database. But for conference Q&A and internal tools, this is sufficient.

Virtual threads generate all embeddings in parallel at startup. 42 chunks, 42 concurrent HTTP calls to Ollama, each on its own virtual thread. Total time: about 2 seconds.

Jakarta Data is the headline feature. @Repository interfaces give you CRUD plus custom queries with zero implementation code. BasicRepository provides save, delete, findById, findAll. @Find generates automatic queries from method parameters. @Query accepts JDQL for anything more complex.

Jakarta Concurrency 3.1 supports virtual threads via @ManagedExecutorDefinition with virtual = true. The container manages the executor lifecycle and propagates Jakarta EE context to virtual threads automatically. We inject it with a CDI qualifier and call submit. No raw JDK Executors. CDI wires everything as application-scoped beans. The ChatModelFactory is a CDI bean with volatile fields for thread-safe model switching. MicroProfile Config externalizes model names and the Ollama URL.

03

Live Build

From empty WAR to RAG in 7 steps

The main event. Seven steps. Each adds one capability. By step 7, you have a complete RAG microservice with runtime model switching. I'll show the actual code, explain the design decisions, and highlight where Jakarta specs do the heavy lifting.

Step 1: JPA Entities with Embeddings

DocumentChunk

@Entity
@Table(name = "document_chunks")
public class DocumentChunk {

  @Id @GeneratedValue(strategy = IDENTITY)
  private Long id;

  @Column(nullable = false, length = 2000)
  private String content;
  private String source;
  private String title;

  @Lob @Column(columnDefinition = "bytea")
  private byte[] embedding;

  public float[] getEmbeddingVector() {
    return EmbeddingConverter.toFloatArray(embedding);
  }

  public void setEmbeddingVector(float[] v) {
    this.embedding = EmbeddingConverter.toByteArray(v);
  }
}

ConferenceTalk

@Entity
@Table(name = "conference_talks")
public class ConferenceTalk {

  @Id @GeneratedValue(strategy = IDENTITY)
  private Long id;
  private String title;
  @Column(length = 2000)
  private String abstractText;
  private String speakerName;
  private String speakerCompany;
  @Column(length = 1000)
  private String speakerBio;
  private String track;
  private String timeSlot;
}

Step one. Two entities. DocumentChunk stores the text segments and their embeddings. ConferenceTalk stores structured conference data.

The embedding field is byte[], stored as PostgreSQL's bytea type. The float[] conversion happens through EmbeddingConverter, a utility with two static methods: toByteArray and toFloatArray, using ByteBuffer. The JPA entity doesn't know about vectors. It stores bytes. The conversion is a concern of the VectorSearch class, not the persistence layer.

ConferenceTalk is a standard JPA entity. Title, abstract, speaker info, track, time slot. Nothing AI-specific. This entity gets seeded from talks.json and then converted into text chunks for embedding.

Step 2: Jakarta Data Repositories

@Repository
public interface Chunks extends BasicRepository<DocumentChunk, Long> {

    @Find
    List<DocumentChunk> findBySource(String source);

    @Query("where source like :pattern order by id asc")
    List<DocumentChunk> findBySourceLike(@Param("pattern") String pattern);

    @Query("select count(this) where source = :source")
    long countBySource(@Param("source") String source);
}

@Repository
public interface Talks extends BasicRepository<ConferenceTalk, Long> {

    @Find
    List<ConferenceTalk> findByTrack(String track);

    @Query("where title like :pattern or abstractText like :pattern")
    List<ConferenceTalk> search(@Param("pattern") String pattern);
}

No implementation class. Payara generates one at runtime. BasicRepository gives CRUD. @Find and @Query add custom methods.

Step two. This is where Jakarta Data shines. Two interfaces, zero implementation classes. Chunks extends BasicRepository, which gives us save, delete, findById, findAll, and more for free. Then we add three custom methods: findBySource for loading chunks by origin, findBySourceLike for pattern matching, and countBySource for the duplicate guard in DataLoader.

Talks is even simpler. findByTrack and a search method that does LIKE matching on title and abstract. JDQL is the query language for Jakarta Data, similar to JPQL but simpler.

Payara generates the implementation at deployment time. You never write a DAO class. You never write a JPQL query string for basic operations. The repository is the abstraction layer between your domain logic and the database.

Step 3: Java Cosine Similarity

@ApplicationScoped
public class VectorSearch {

    @Inject Chunks chunks;
    @Inject EmbeddingModel embeddingModel;

    public List<DocumentChunk> search(String query, int maxResults) {
        float[] queryVec = embeddingModel.embed(query).content().vector();

        return chunks.findAll().toList().stream()
            .filter(c -> c.getEmbedding() != null)
            .map(c -> new SimilarityResult(c,
                cosineSimilarity(queryVec, c.getEmbeddingVector())))
            .sorted(comparingDouble(SimilarityResult::score).reversed())
            .limit(maxResults)
            .map(SimilarityResult::chunk)
            .toList();
    }

    static double cosineSimilarity(float[] a, float[] b) { /* 15 lines */ }
}

No vector database. Load chunks from Jakarta Data repository, compute similarity in Java. 15 lines of math replaces an entire infrastructure dependency.

Step three. The VectorSearch class is the replacement for PgVector, Pinecone, Weaviate, or any vector database. It embeds the query using the Ollama embedding model, loads all chunks from the Chunks repository, computes cosine similarity between the query vector and each chunk's stored vector, sorts by score, and returns the top results.

The cosineSimilarity method is pure math: dot product divided by the product of magnitudes. 15 lines. Returns a score between 0 and 1 where 1 means identical. The SimilarityResult record pairs each chunk with its score for sorting.

Tradeoff: this loads all chunks into memory. For 42 chunks, that's negligible. For 42 million, you'd want a vector database with an index. But for the vast majority of internal AI tools, conference assistants, documentation Q&A systems, this approach is sufficient and avoids an entire infrastructure dependency.

Step 4: Programmatic RAG

@ApplicationScoped
public class AiService {

    @Inject ChatModelFactory modelFactory;
    @Inject VectorSearch vectorSearch;

    public String ask(String question) {
        List<DocumentChunk> chunks = vectorSearch.search(question, 5);

        String context = chunks.stream()
            .map(c -> "Source: " + c.getSource() + "\n" + c.getContent())
            .collect(Collectors.joining("\n\n"));

        String userMessage = """
            Context:
            %s

            Question: %s
            """.formatted(context, question);

        return modelFactory.getChatModel()
            .chat(ChatRequest.builder()
                .messages(UserMessage.from(userMessage)).build())
            .aiMessage().text();
    }
}

Embed query → find similar chunks → build prompt → call LLM. ~25 lines. Zero framework magic.

Step four. The AiService is the entire RAG pipeline in one method. First, VectorSearch finds the 5 most similar chunks. Then we format them as context with source labels. Then we build a user message that combines the context and the question. Finally, we call the chat model through ChatModelFactory and return the response text.

Compare this to the declarative approach from my first talk: an interface with @SystemMessage, wired by AiServices.builder(). That's 5 lines. This is 25. The tradeoff: 25 lines you can debug, modify, and extend without framework constraints. Want to add a minimum relevance threshold? Add an if statement. Want to log which chunks were retrieved? Add a log statement. Want to change the prompt format at runtime? It's a string template, not an annotation.

And critically: the ChatModelFactory enables runtime model switching, which the declarative approach cannot do.

Step 5: Runtime Model Switching

@ApplicationScoped
public class ChatModelFactory {

    private volatile ChatModel chatModel;
    private volatile String currentModelName;

    @PostConstruct
    void init() {
        String modelName = ConfigProvider.getConfig()
            .getValue("ollama.chat.model", String.class);
        this.chatModel = createChatModel(modelName);
        this.currentModelName = modelName;
    }

    public void switchModel(String modelName) {
        this.chatModel = createChatModel(modelName);
        this.currentModelName = modelName;
    }

    private ChatModel createChatModel(String name) {
        return OllamaChatModel.builder()
            .baseUrl(baseUrl).modelName(name)
            .temperature(0.7).timeout(Duration.ofSeconds(300))
            .build();
    }
}

Step five. This is the feature you can't get with @RegisterAIService. The ChatModelFactory holds the current ChatModel in a volatile field. On startup, it reads the default model from MicroProfile Config. The switchModel method creates a new OllamaChatModel with the requested model name and atomically replaces the reference.

Volatile ensures visibility across threads. When one request switches the model, the next request sees the new model. Reference assignment is atomic in Java, so no synchronization needed. We never mutate the model object itself; we replace the whole reference.

The createChatModel method reads the base URL and timeout from MicroProfile Config, then builds an OllamaChatModel with the specified model name. Changing from gemma3 to mistral is one builder call. No redeployment. No restart. One HTTP POST to the /api/models endpoint.

Step 6: Virtual Thread Ingestion

Configuration

@ApplicationScoped
@ManagedExecutorDefinition(
    name = "java:module/concurrent/"
         + "VirtualThreadExecutor",
    virtual = true,
    qualifiers = VirtualThreadExecutor.class
)
public class ConcurrencyConfig {}

Ingestion

@Inject @VirtualThreadExecutor
ManagedExecutorService executor;

private void generateEmbeddings(
        List<DocumentChunk> chunks) {
    List<Future<Void>> futures =
      chunks.stream()
        .map(c -> executor.submit(() -> {
          Response<Embedding> r =
            embeddingModel.embed(c.getContent());
          c.setEmbeddingVector(
            r.content().vector());
          return null;
        }))
        .toList();

    for (Future<Void> f : futures)
        f.get();
}

Container-managed virtual threads. No raw JDK executors. Context propagation handled by the platform.

Step six. The DataLoader generates embeddings at startup. Each chunk makes an HTTP call to Ollama's embedding endpoint. Instead of raw JDK Executors, we use Jakarta Concurrency 3.1's @ManagedExecutorDefinition with virtual = true.

The configuration is one annotation on one class. Payara creates a ManagedExecutorService backed by virtual threads, registers it in JNDI, and makes it available for CDI injection via the VirtualThreadExecutor qualifier. The DataLoader injects it and calls submit for each chunk.

Why this over Executors.newVirtualThreadPerTaskExecutor()? Context propagation. The managed executor automatically propagates Jakarta EE context to virtual threads: transactions, security, classloading. The raw JDK executor drops all of that. For this use case it wouldn't matter since we're not inside a transaction on the worker threads, but it's the idiomatic Jakarta EE pattern and it matters for production code.

42 chunks means 42 virtual threads submitted to the managed executor, all running concurrently. When a virtual thread blocks on the HTTP response, the JVM unmounts it from the carrier thread and schedules another. Total time: about 2 seconds.

Step 7: REST Endpoints

ChatResource

@Path("/chat")
public class ChatResource {

    @Inject AiService aiService;

    @POST
    @Consumes(APPLICATION_FORM_URLENCODED)
    @Produces(TEXT_HTML)
    public String ask(
            @FormParam("question") String q) {
        String answer = aiService.ask(q);
        return renderAnswer(q, answer);
    }
}

ModelResource

@Path("/models")
public class ModelResource {

    @Inject ChatModelFactory factory;

    @GET @Produces(APPLICATION_JSON)
    public Map<String, Object> list() {
        return Map.of("current",
            factory.getCurrentModelName(),
            "available",
            factory.getAvailableModels());
    }

    @POST
    public String switchModel(
            @FormParam("model") String name) {
        factory.switchModel(name);
        return "<strong>" + name + "</strong>";
    }
}

Step seven. Two JAX-RS resources. ChatResource handles the Q&A form post. HTMX sends the question as form data, the resource calls AiService, renders the markdown answer to HTML using CommonMark, and returns an HTML fragment that HTMX injects into the page.

ModelResource is the runtime switching API. GET returns the current model name and available models as JSON. POST accepts a model name, calls factory.switchModel, and returns an HTML fragment that updates the model indicator in the UI. No redeployment. No restart. The next chat request uses the new model.

Both endpoints are standard JAX-RS. No AI framework annotations. No special configuration. Just CDI injection and HTTP.

04

Virtual Threads

Why they matter for AI workloads

Let me spend a minute on virtual threads because they're the enabling technology for this approach. Without virtual threads, parallel embedding generation requires thread pool configuration. With Jakarta Concurrency 3.1, it's one annotation.

Platform vs Virtual Threads

Platform Threads Virtual Threads
Memory ~1MB stack per thread ~1KB per thread
Creation OS syscall, expensive JVM-managed, cheap
Blocking I/O Pins carrier thread Auto-unmounts, frees carrier
Pool sizing Must tune for workload @ManagedExecutorDefinition(virtual=true)
50 concurrent HTTP calls 50MB heap, FixedThreadPool(50) 50KB heap, no config

The numbers tell the story. A platform thread reserves about 1MB of stack space. A virtual thread uses about 1KB. That's a 1000x difference. For 50 concurrent HTTP calls to Ollama, platform threads consume 50MB. Virtual threads consume 50KB.

The real win isn't memory. It's the elimination of pool sizing. Every Java developer has stared at a thread pool configuration wondering: should it be 10? 50? 200? The answer depends on the workload, and the workload changes. Jakarta Concurrency 3.1 makes the question irrelevant. @ManagedExecutorDefinition with virtual = true gives you a container-managed executor backed by virtual threads. Submit as many tasks as you need. The JVM multiplexes them onto a small pool of carrier threads.

When a virtual thread makes a blocking HTTP call, the JVM unmounts it from the carrier thread. The carrier thread runs another virtual thread. When the HTTP response arrives, the virtual thread remounts and continues. This is automatic. No reactive programming. No CompletableFuture chains. Just blocking code that scales.

Virtual Thread Caveats

Avoid

  • synchronized blocks — pins carrier thread
  • ThreadLocal abuse — each vthread gets its own
  • CPU-bound work — use platform threads instead

Prefer

  • ReentrantLock instead of synchronized
  • I/O-bound work — HTTP calls, DB queries
  • Short-lived tasks — create, block, complete

Virtual threads excel at many concurrent I/O-bound operations. AI embedding generation is the textbook use case: lots of HTTP calls, each blocking for a response.

A few caveats worth knowing. Synchronized blocks pin the virtual thread to its carrier, defeating the purpose. Use java.util.concurrent.locks.ReentrantLock instead. In our code, we don't use any locks at all, so this isn't an issue.

ThreadLocal is per-virtual-thread. If you create a million virtual threads with ThreadLocal state, you get a million copies. Be careful. Our code doesn't use ThreadLocal.

Virtual threads are for I/O-bound work. CPU-bound work like matrix multiplication should stay on platform threads. Our embedding generation is I/O-bound: it makes an HTTP call to Ollama and waits for the response. The actual math happens in Ollama, not in the JVM. This is the ideal virtual thread workload.

05

Runtime Model Switching

One HTTP POST. No redeployment.

This is the feature that justifies the programmatic approach. With the declarative @RegisterAIService, the AI service is created once at deployment time. To change the model, you redeploy. With ChatModelFactory, you send one HTTP POST and the next request uses the new model.

Declarative vs Programmatic

Declarative (Talk 1)

@SystemMessage("You are an expert...")
public interface Assistant {
    String ask(@UserMessage String q);
}

// Wiring:
assistant = AiServices.builder(
    Assistant.class)
  .chatModel(chatModel)
  .contentRetriever(retriever)
  .build();
  • ~5 lines of config
  • Cannot switch model at runtime

Programmatic (Talk 2)

// AiService asks the factory:
ChatModel model = modelFactory.getChatModel();
return model.chat(request).aiMessage().text();

// Switch at runtime:
modelFactory.switchModel("mistral");
// Next request uses mistral
  • ~25 lines of pipeline code
  • Runtime switching via volatile field

Side by side. On the left, the declarative approach from Talk 1. An interface with annotations, wired by AiServices.builder(). About 5 lines of configuration. Very clean. But the AI service is immutable after construction. You can't change the model without rebuilding.

On the right, the programmatic approach. The AiService asks the ChatModelFactory for the current model on every request. The factory holds the model in a volatile field. When switchModel is called, the factory creates a new OllamaChatModel with the requested model name and atomically replaces the reference. The next request picks up the new model.

This is a deliberate tradeoff. 20 more lines of code in exchange for runtime flexibility. For a production system where you might want to A/B test models or fall back from a large model to a small one under load, this matters.
