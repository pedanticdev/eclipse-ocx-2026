01

The Claim

Boring stack. Smart AI.

Here is the standard narrative about AI in Java. You want AI, you need Python, a vector database, a separate service, and a thread pool tuned to your CPU cores. Every one of those assumptions gets challenged in this section with working code. First, the problems that narrative is supposedly solving.

The Problem

Thread Pools

  • Fixed pool sizing for AI I/O
  • One blocking call = one pinned thread
  • 50 concurrent requests = 50MB of stack

Vector Data

  • 768 floats per embedding
  • Don't fit JPA entities
  • "Need a vector database"

Python Dependency

  • All examples in Python
  • Separate team, deploy, monitor
  • Context-switching tax

Three problems I keep hearing. Thread pools: your Java app makes blocking HTTP calls to the LLM, each call ties up a platform thread for seconds, and picking a pool size is a no-win choice; too small and requests queue, too big and you run out of memory. Vector data: embeddings are arrays of 768 floats, JPA doesn't have a vector column type, and people conclude you need a separate vector database. Python: every AI tutorial is written in Python, your team writes Java, and suddenly you need two ecosystems to ship one feature.

None of these are unsolvable. They are architectural decisions, and the standard answers are overengineered. The counter-claim is the next slide.

The Boring Stack is the Smartest Choice

No Vector DB
No Python
No Thread Pool Tuning

Virtual threads handle concurrency. Jakarta Data handles persistence. Java handles similarity. Same spec, new capabilities.

Three things you won't need. First, no separate vector database: embeddings live as byte arrays on a JPA entity, Jakarta Data repositories load the chunks, and cosine similarity runs in Java on the result in fifteen lines of math. Second, no Python: LangChain4j is the Java-native equivalent of Python's LangChain and lives happily inside a WAR. Third, no thread pool tuning: virtual threads on Java 21 give you millions of concurrent tasks without configuring a single pool size.

The core claim is that your existing Jakarta EE knowledge composes naturally with AI workloads. You don't need to learn a new stack; you need to use the one you have correctly. With that established, let's look at what "the stack" actually means in practice.

This slide names the architectural choice directly. The declarative alternative, LangChain4j's @RegisterAIService with its CDI portable extension and something like PgVector, gets you a working RAG pipeline in about four lines of configuration. It is a legitimate option and for many teams it is the right one. But it has a ceiling: the CDI extension wires the AI service at deployment time, so you cannot swap the model at runtime.

This talk trades convenience for control. We build RAG from scratch: embed the query, find similar chunks, build the prompt, call the model. About thirty more lines of code. In exchange we get runtime model switching, database-persistent embeddings, and a complete understanding of every moving part, with no generated code or framework-specific annotations beyond standard Jakarta. Live Build

From empty WAR to RAG in 7 steps

The main event. Seven steps, each adding one capability. By step seven we have a complete RAG microservice with runtime model switching. I will show the actual code, explain the design decisions, and highlight where Jakarta specs do the heavy lifting. Step one is the entities.

Step 1: JPA Entities with Embeddings

DocumentChunk

@Entity
@Table(name = "document_chunks")
public class DocumentChunk {

  @Id @GeneratedValue(strategy = IDENTITY)
  private Long id;

  @Column(nullable = false, length = 2000)
  private String content;
  private String source;
  private String title;

  @Lob @Column(columnDefinition = "bytea")
  private byte[] embedding;

  public float[] getEmbeddingVector() {
    return EmbeddingConverter.toFloatArray(embedding);
  }

  public void setEmbeddingVector(float[] v) {
    this.embedding = EmbeddingConverter.toByteArray(v);
  }
}

ConferenceTalk

@Entity
@Table(name = "conference_talks")
public class ConferenceTalk {

  @Id @GeneratedValue(strategy = IDENTITY)
  private Long id;
  private String title;
  @Column(length = 2000)
  private String abstractText;
  private String speakerName;
  private String speakerCompany;
  @Column(length = 1000)
  private String speakerBio;
  private String track;
  private String timeSlot;
}

Step one. Two entities. DocumentChunk stores the text segments and their embeddings. ConferenceTalk stores structured conference data.

The embedding field is a byte array, stored as PostgreSQL's bytea type. The conversion to and from a float array happens through EmbeddingConverter, a utility with two static methods backed by ByteBuffer. The JPA entity doesn't know about vectors; it just stores bytes. The conversion is a concern of the VectorSearch class, not the persistence layer.

ConferenceTalk is a standard JPA entity: title, abstract, speaker info, track, time slot, nothing AI-specific. It gets seeded from talks.json at startup and then converted into text chunks for embedding. Entities on their own are not useful until we can load them, which brings us to the repositories.

Step 2: Jakarta Data Repositories

@Repository
public interface Chunks extends BasicRepository<DocumentChunk, Long> {

    @Find
    List<DocumentChunk> findBySource(String source);

    @Query("where source like :pattern order by id asc")
    List<DocumentChunk> findBySourceLike(@Param("pattern") String pattern);

    @Query("select count(this) where source = :source")
    long countBySource(@Param("source") String source);
}

@Repository
public interface Talks extends BasicRepository<ConferenceTalk, Long> {

    @Find
    List<ConferenceTalk> findByTrack(String track);

    @Query("where title like :pattern or abstractText like :pattern")
    List<ConferenceTalk> search(@Param("pattern") String pattern);
}

No implementation class. Payara generates one at runtime. BasicRepository gives CRUD. @Find and @Query add custom methods.

Step two, where Jakarta Data earns its keep. Two interfaces, zero implementation classes. Chunks extends BasicRepository, which gives us save, delete, findById, findAll, and more for free. Then we add three custom methods: findBySource for loading chunks by origin, findBySourceLike for pattern matching, and countBySource for the duplicate guard in DataLoader.

Talks is even simpler: findByTrack and a search method that does LIKE matching on title and abstract. JDQL is the query language for Jakarta Data, similar to JPQL but simpler.

Payara generates the implementation at deployment time. You never write a DAO class and you never write a JPQL query string for basic operations. The repository is the abstraction layer between your domain logic and the database. Before we move on, quick receipts on exactly what this replaces.

Step 3: Java Cosine Similarity

@ApplicationScoped
public class VectorSearch {

    @Inject Chunks chunks;
    @Inject EmbeddingModel embeddingModel;

    public List<DocumentChunk> search(String query, int maxResults) {
        float[] queryVec = embeddingModel.embed(query).content().vector();

        return chunks.findAll().toList().stream()
            .filter(c -> c.getEmbedding() != null)
            .map(c -> new SimilarityResult(c,
                cosineSimilarity(queryVec, c.getEmbeddingVector())))
            .sorted(comparingDouble(SimilarityResult::score).reversed())
            .limit(maxResults)
            .map(SimilarityResult::chunk)
            .toList();
    }

    static double cosineSimilarity(float[] a, float[] b) { /* 15 lines */ }
}

No vector database. Load chunks from Jakarta Data repository, compute similarity in Java. 15 lines of math replaces an entire infrastructure dependency.

Step three. The VectorSearch class is the replacement for PgVector, Pinecone, Weaviate, or any vector database. It embeds the query using the Ollama embedding model, loads all chunks from the Chunks repository, computes cosine similarity between the query vector and each chunk's stored vector, sorts by score, and returns the top results.

The cosineSimilarity method is pure math: dot product divided by the product of magnitudes. Fifteen lines. It returns a score between zero and one, where one means identical. The SimilarityResult record pairs each chunk with its score for sorting.

One tradeoff worth naming. This loads all chunks into memory. For fifty chunks that is negligible. For fifty million you would want a vector database with an index. For the vast majority of internal AI tools, conference assistants, and documentation Q&A systems, this approach is sufficient and avoids an entire infrastructure dependency. With search in hand, we wrap it with the orchestration that calls the model.

Step 4: Programmatic RAG

@ApplicationScoped
public class AiService {

    @Inject ChatModelFactory modelFactory;
    @Inject VectorSearch vectorSearch;

    public String ask(String question) {
      try {
        List<DocumentChunk> chunks = vectorSearch.search(question, 10);
        if (chunks.isEmpty()) return "No relevant info found.";

        String context = chunks.stream()
            .map(c -> "Source: " + c.getSource() + "\n" + c.getContent())
            .collect(Collectors.joining("\n\n"));

        String userMessage = """
            Context: %s
            Question: %s""".formatted(context, question);

        return modelFactory.getChatModel()
            .chat(ChatRequest.builder()
                .messages(UserMessage.from(userMessage)).build())
            .aiMessage().text();
      } catch (Exception e) {
        return "Model unavailable: " + e.getMessage();
      }
    }
}

Embed query → find similar chunks → build prompt → call LLM. ~25 lines. Zero framework magic.

Step four. The AiService is the entire RAG pipeline in one method. First, VectorSearch finds the ten most similar chunks. Then we format them as context with source labels. Then we build a user message that combines the context and the question. Finally, we call the chat model through ChatModelFactory and return the response text.

The declarative alternative is an interface with @SystemMessage and @UserMessage, wired by AiServices.builder(). About five lines. This is twenty-five. The tradeoff is twenty-five lines you can debug, modify, and extend without framework constraints. Adding a relevance threshold is an if statement. Logging which chunks were retrieved is a log line. Changing the prompt format at runtime is a string edit, which an annotation cannot give you.

The critical piece that makes this worth twenty extra lines is the ChatModelFactory, which enables runtime model switching. That factory is step five.

Step 5: Runtime Model Switching

@ApplicationScoped
public class ChatModelFactory {

    @Inject @ConfigProperty(name = "ollama.base.url")
    private String baseUrl;
    @Inject @ConfigProperty(name = "ollama.chat.model")
    private String defaultModelName;
    @Inject @ConfigProperty(name = "ollama.chat.temperature",
                            defaultValue = "0.7")
    private double temperature;
    @Inject @ConfigProperty(name = "ollama.chat.timeout",
                            defaultValue = "300")
    private int timeoutSeconds;

    private volatile ChatModel chatModel;
    private volatile String currentModelName;

    @PostConstruct
    void init() {
        this.chatModel = createChatModel(defaultModelName);
        this.currentModelName = defaultModelName;
    }

    public void switchModel(String modelName) {
        this.chatModel = createChatModel(modelName);
        this.currentModelName = modelName;
    }

    private ChatModel createChatModel(String name) {
        return OllamaChatModel.builder()
            .baseUrl(baseUrl).modelName(name)
            .temperature(temperature)
            .timeout(Duration.ofSeconds(timeoutSeconds))
            .build();
    }
}

The volatile field is the whole point. We'll see what it buys us in Part 5, and swap models live in the demo.

Step five. Config values are injected via @ConfigProperty rather than the imperative ConfigProvider.getConfig(). The CDI approach is the idiomatic Jakarta EE pattern: type-safe, testable, and the container handles conversion and defaults.

The ChatModelFactory holds the current ChatModel in a volatile field. On startup, @PostConstruct reads the default model name from the injected config and builds the initial model. The switchModel method creates a new OllamaChatModel with the requested name and atomically replaces the reference.

Volatile ensures visibility across threads. When one request switches the model, the next request sees the new model. Reference assignment is atomic in Java, so no synchronization is needed. Changing from gemma4 to mistral is one builder call triggered by a single HTTP POST to /api/models, with no redeployment or restart required. The volatile field is the whole point of the programmatic approach; we will return to why in Part 5. Next, parallel ingestion.

Step 6: Virtual Thread Ingestion

Configuration

@ApplicationScoped
@ManagedExecutorDefinition(
    name = "java:module/concurrent/"
         + "VirtualThreadExecutor",
    virtual = true,
    qualifiers = VirtualThreadExecutor.class
)
public class ConcurrencyConfig {}

Ingestion

@Inject @VirtualThreadExecutor
ManagedExecutorService executor;

private void generateEmbeddings(
        List<DocumentChunk> chunks) {
    List<Future<Void>> futures =
      chunks.stream()
        .map(c -> executor.submit(() -> {
          Response<Embedding> r =
            embeddingModel.embed(c.getContent());
          c.setEmbeddingVector(
            r.content().vector());
          return null;
        }))
        .toList();

    for (Future<Void> f : futures)
        f.get();
}

Container-managed virtual threads. No raw JDK executors. Context propagation handled by the platform.

Step six. The DataLoader generates embeddings at startup. Each chunk makes an HTTP call to Ollama's embedding endpoint. Instead of raw JDK Executors, we use Jakarta Concurrency 3.1's @ManagedExecutorDefinition with virtual set to true.

The configuration is one annotation on one class. Payara creates a ManagedExecutorService backed by virtual threads, registers it in JNDI, and makes it available for CDI injection via the VirtualThreadExecutor qualifier. The DataLoader injects it and calls submit for each chunk.

Why this over Executors.newVirtualThreadPerTaskExecutor? Context propagation. The managed executor automatically propagates Jakarta EE context to virtual threads: transactions, security, classloading. The raw JDK executor drops all of that. For this use case it would not matter since we are not inside a transaction on the worker threads, but it is the idiomatic Jakarta EE pattern and it matters for production code.

About fifty chunks means about fifty virtual threads submitted to the managed executor, all running concurrently. When a virtual thread blocks on the HTTP response, the JVM unmounts it from the carrier thread and schedules another. Total time is a couple of seconds, bounded by Ollama's parallel embedding slots. The final piece is exposing all of this over HTTP.

04

Virtual Threads

Why they matter for AI workloads

A minute on virtual threads, because they are the enabling technology for everything we just demoed. Without virtual threads, parallel embedding generation requires thread pool configuration, and concurrent requests queue on whatever pool size you picked at deploy time. With Jakarta Concurrency 3.1, it is one annotation. The comparison is worth making explicit.

Platform vs Virtual Threads

Platform Threads Virtual Threads
Memory ~1MB stack per thread ~1KB per thread
Creation OS syscall, expensive JVM-managed, cheap
Blocking I/O Pins carrier thread Auto-unmounts, frees carrier
Pool sizing Must tune for workload @ManagedExecutorDefinition(virtual=true)
50 concurrent HTTP calls 50MB heap, FixedThreadPool(50) 50KB heap, no config

The numbers tell the story. A platform thread reserves about one megabyte of stack space. A virtual thread uses about one kilobyte. That is a thousand-times difference. For fifty concurrent HTTP calls to Ollama, platform threads consume fifty megabytes, while virtual threads consume fifty kilobytes.

The real win is not memory; it is the elimination of pool sizing. Every Java developer has stared at a thread pool configuration wondering whether it should be ten, fifty, or two hundred. The answer depends on the workload, and the workload changes. Jakarta Concurrency 3.1 makes the question irrelevant: @ManagedExecutorDefinition with virtual set to true gives you a container-managed executor backed by virtual threads. Submit as many tasks as you need, and the JVM multiplexes them onto a small pool of carrier threads.

When a virtual thread makes a blocking HTTP call, the JVM unmounts it from the carrier thread. The carrier thread runs another virtual thread. When the HTTP response arrives, the virtual thread remounts and continues. This is automatic; you don't need reactive programming or CompletableFuture chains because blocking code scales on its own. With that said, there are a few caveats.

Virtual Thread Caveats

Avoid

  • synchronized blocks — pins carrier thread
  • ThreadLocal abuse — each vthread gets its own
  • CPU-bound work — use platform threads instead

Prefer

  • ReentrantLock instead of synchronized
  • I/O-bound work — HTTP calls, DB queries
  • Short-lived tasks — create, block, complete

Virtual threads excel at many concurrent I/O-bound operations. AI embedding generation is the textbook use case: lots of HTTP calls, each blocking for a response.

Three caveats worth knowing. Synchronized blocks pin the virtual thread to its carrier, defeating the purpose. Use java.util.concurrent.locks.ReentrantLock instead. In our code we don't use any locks at all, so this is not an issue.

ThreadLocal is per-virtual-thread. If you create a million virtual threads with ThreadLocal state, you get a million copies, so treat that carefully. Our code does not use ThreadLocal either.

Virtual threads are for I/O-bound work. CPU-bound work like matrix multiplication should stay on platform threads. Our embedding generation is I/O-bound because it makes an HTTP call to Ollama and waits for the response, while the actual math happens in Ollama, not in the JVM. This is the ideal virtual thread workload, which is exactly what the benchmark demoed a moment ago. Here is the code behind it.

Virtual Threads in the Request Path

@ApplicationScoped
public class BenchmarkService {

    @Inject @VirtualThreadExecutor
    ManagedExecutorService executorService;
    @Inject AiService aiService;

    public BenchmarkResult run(List<String> questions) {
        List<CompletableFuture<QuestionResult>> futures =
          questions.stream()
            .map(q -> CompletableFuture.supplyAsync(
                () -> askQuestion(q), executorService))
            .toList();

        CompletableFuture.allOf(
            futures.toArray(CompletableFuture[]::new))
          .join();

        return collectResults(futures);
    }
}

Java never queues. Virtual threads submit all N requests the instant the user clicks. Wall-clock time is bound by OLLAMA_NUM_PARALLEL, not by a Java thread pool.

Same virtual thread executor you saw in Step 6, now in the request path rather than at startup. Each question is submitted to the managed executor as a supplyAsync call, the executor creates a virtual thread for each one, CompletableFuture.allOf blocks until all complete, and then we collect timing data.

The point I want you to take away is that Java contributes zero queuing. All N requests hit Ollama simultaneously. From there, Ollama decides how many run in parallel via OLLAMA_NUM_PARALLEL, which the compose file sets to eight. So twenty questions means twenty virtual threads submitted immediately, eight in-flight at Ollama, and twelve waiting at the inference server, not at the Java layer.

That split matters. Without virtual threads, your Java thread pool is the first bottleneck. A FixedThreadPool(20) pins twenty megabytes of stack; a FixedThreadPool(8) forces you to pick a pool size that assumes you know Ollama's capacity ahead of time. Virtual threads let you decouple the two: scale the submission side for free, scale the inference side with a single env var. Two independent knobs instead of one tangled decision. That covers virtual threads. On to the payoff.

The Payoff

Reflecting on the programmatic vs declarative choice.

You just saw the runtime model switch in the demo. Now a short reflection on why we took the programmatic path instead of the declarative one, and when each is the right call. The answer is not "programmatic wins"; the answer is "pick the one that matches your operational needs". Here they are side by side.

Declarative vs Programmatic

Declarative

@RegisterAIService
@SystemMessage("You are an expert...")
public interface Assistant {
    String ask(@UserMessage String q);
}

// Container wires the RAG pipeline
// at deployment time.
  • ~5 lines, zero glue code
  • Fastest path to a working RAG
  • Model baked in at deploy
  • No swap without redeploy

Programmatic

// Every request asks the factory:
ChatModel m = modelFactory.getChatModel();
return m.chat(request).aiMessage().text();

// Hot-swap the model at runtime:
modelFactory.switchModel("mistral");
// Next request uses mistral.
  • ~25 lines of explicit pipeline
  • Runtime swap via volatile field
  • A/B testing, graceful fallback

Both are legitimate. Pick declarative when the model is fixed. Pick programmatic when you need to change models without a redeploy.

Side by side. On the left, the declarative approach: an interface with @RegisterAIService, wired by LangChain4j's CDI portable extension. About five lines. Very clean. But the AI service is immutable after construction, so you cannot change the model without rebuilding.

On the right, the programmatic approach we walked through. The AiService asks the ChatModelFactory for the current model on every request. The factory holds the model in a volatile field. When switchModel is called, the factory creates a new OllamaChatModel with the requested name and atomically replaces the reference. The next request picks up the new model.

This is a deliberate tradeoff. About twenty extra lines of code in exchange for runtime flexibility. If you know your model at deploy time, declarative is the right answer. If you need A/B testing, graceful fallback under load, or tenant-specific model routing, programmatic pays for itself the first time you use it. Before we close, one honest slide about where this approach stops working.

Where This Approach Breaks

Limit What fails What to do
Millions of vectors Cosine in Java is O(n) per query PgVector with an HNSW index, or a dedicated vector DB
CPU-only inference gemma4:e2b takes seconds per request Point OLLAMA_BASE_URL at a GPU host, same WAR
Horizontal scaling volatile field is per-instance Push model choice to MicroProfile Config + a config refresh
Strict session consistency In-flight request may use previous model Pin model per session, or quiesce before switching
Long-running tool use Single ChatRequest, no function calls shown LangChain4j tool-use API on top of the same factory

Knowing the edges is the difference between a pattern and a fad. This is the pattern. Here are the edges.

I said at the start that I reject the standard "you need Python" narrative. I am not going to turn around and claim this approach scales to everything. Here is where it breaks.

Cosine similarity in Java is linear in the number of chunks. A few thousand is fine, millions is not. When you reach that point, PgVector with an HNSW index is the smallest step up: same database, same JPA entity, add the extension and swap VectorSearch for an indexed query.

CPU-only inference is slow. gemma4:e2b on a laptop CPU is multiple seconds per request. Point OLLAMA_BASE_URL at a GPU host and the same WAR goes ten to fifty times faster with no code change.

The volatile-field model switch is per-JVM. If you run five instances behind a load balancer, switching the model on one does not touch the others. The production answer is to push the current model name through MicroProfile Config with a config source that refreshes on change.

And if you need tool use, multi-turn conversations, or structured output, LangChain4j's higher-level API is where you pick it up; it composes cleanly with the factory we built. Knowing the edges is the difference between a pattern and a fad. With that honesty established, the takeaways.
